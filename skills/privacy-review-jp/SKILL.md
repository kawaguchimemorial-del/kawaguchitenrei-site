# Skill: 日本向け Privacy Review（個人情報保護レビュー）

## 目的

葬儀社という業界特性上、ご遺族・故人・喪主・参列者の個人情報保護が最優先事項。
本 Skill は、画像・本文・フォーム・ログ・JSON-LD など、サイトに掲載する情報に個人特定リスクが含まれていないかを確認するための手順。

## 適用範囲

- 施行事例（`/case/[slug]/`）の追加・更新
- お客様の声（`/voice/[slug]/`）の追加・更新
- 画像追加（`public/images/**`）、特に施行事例・お客様の声・式場内観・面会室
- フォーム改修（`app/contact/**`・`app/estimate/**`・`app/api/**`）
- スタッフ紹介・代表挨拶（実名出現時）
- JSON-LD への Review / Person / customer 系プロパティ追加（**原則禁止**だが追加要望時はチェック）

## 確認対象と確認方法

### A. 画像

| 確認項目 | 方法 | NG パターン |
|---|---|---|
| 遺影が写っているか | 目視 | 顔写真 / 名前付きの遺影 |
| 名札・席札・会葬礼状が読めるか | 目視 + 拡大確認 | 苗字 / 戒名 / 喪主名が文字認識可能 |
| 供花の名札が読めるか | 目視 + 拡大確認 | 贈り主の名前・社名が読める |
| 参列者の顔が判別できるか | 目視 | プライバシーモザイク未処理 |
| 棺・骨壺が大きく写っているか | 目視 | 故人を想起させる過度に直接的な画像 |
| スタッフが写っている場合、本人同意があるか | 確認記録 | 同意なしの個人特定可能な写真 |
| アンケート画像（手書き）の文字認識 | 目視 + 拡大 | 個人名 / 住所 / 電話番号が読める |

### B. 本文（コードまたは JSON データ）

| 確認項目 | 方法 | NG パターン |
|---|---|---|
| 故人の実名 | grep + 目視 | フルネーム / 苗字 + 続柄 |
| 喪主の実名 | grep + 目視 | フルネーム / 苗字 + 続柄 |
| ご遺族の実名 | grep + 目視 | お子様・配偶者・親族の名前 |
| スタッフの実名（事例担当者） | grep + 目視 + 本人同意確認 | 本人同意なしの実名 |
| 個別事例の特定可能な日付 | grep + 判断 | 日付 + 施設名 + 規模 で個人特定可能 |
| 住所（個人宅） | grep | 番地・部屋番号レベル |
| 電話番号（個人） | grep（数字パターン） | 個人の固定電話・携帯電話 |
| メールアドレス（個人） | grep（`@` パターン） | 個人のメール |
| 故人の病歴・死因 | 目視 | 医療情報 |
| 宗教・宗派の個別事例 | 目視 | 寺院名 + 故人特定 |

### C. フォーム

| 確認項目 | 方法 | NG パターン |
|---|---|---|
| 入力値のログ出力 | コード Grep | console.log / Sentry に個人情報が出る |
| エラーメッセージに個人情報が含まれるか | 目視 | 「<入力されたメール> はすでに登録されています」など |
| 入力値が URL クエリパラメータに乗るか | コード Grep | GET 送信になっていないか |
| 送信先（Webhook URL）が公開コードに含まれないか | grep | URL が `.env.local` のみ参照されているか |
| reCAPTCHA / honeypot などの bot 対策 | 確認 | フォーム改修時に壊れていないか |
| バリデーション・サニタイズ | レビュー | XSS / SQL インジェクション対策 |

### D. JSON-LD

| 確認項目 | 方法 | NG パターン |
|---|---|---|
| Review / Person 型 | grep `"@type":"Review"` / `"@type":"Person"` | 個別顧客名・実名が含まれる |
| aggregateRating / ratingValue | grep | 根拠のない評価値、または顧客同意なしの集計 |
| author プロパティに個人名 | grep `"author"` | 顧客名・喪主名が含まれる |
| customer プロパティ | grep | 顧客 ID・実名が含まれる |

## 標準 5 ステップ

### Step 1: 対象範囲の特定

- 変更対象ファイルを列挙
- 画像追加なら画像ファイルパスを列挙
- 本文追加なら追加箇所の Diff を確認

### Step 2: 自動チェック（grep）

```sh
# 個人情報パターン grep の例
grep -rn -E "(故人|喪主|遺族).*様?[^\}]*様" <target>
grep -rn -E "@.*\.(co\.jp|com|jp|net)" <target>  # メール
grep -rn -E "[0-9]{2,4}-[0-9]{2,4}-[0-9]{3,4}" <target>  # 電話
grep -rn -E "\"@type\":\"(Review|Person)\"" <target>  # JSON-LD
grep -rn -E "aggregateRating|ratingValue" <target>
```

### Step 3: 目視確認

- 画像: ピクセル等倍 or 拡大して文字・顔の判別可能性を確認
- 本文: 文脈で個人特定が可能になっていないか確認
- フォーム: 実際の送信フローを開発環境で目視

### Step 4: 人間承認の要否判定

| 該当 | 対応 |
|---|---|
| A / B / C / D のいずれかで NG パターンを発見 | **即停止、人間に報告**。掲載しない |
| 個人特定リスクは低いが確信が持てない | **人間承認待ち**。push 前に確認を求める |
| すべてクリア | 通常フローへ進む |

### Step 5: 記録

- `docs/04-privacy-review.md` のチェックリストに従って結果を記録
- 個別案件は `docs/eval/records/<日付>-privacy-review-<件名>.md` に保存（必要な場合）

## チェックリスト

| 項目 | 確認 |
|---|---|
| 個人名・故人名・喪主名 0 件 | ☐ |
| 遺影・名札・会葬礼状の判読 0 件 | ☐ |
| 個人宅住所・個人電話番号 0 件 | ☐ |
| 個人メールアドレス 0 件 | ☐ |
| スタッフ実名出現時の本人同意確認 | ☐ |
| 故人の病歴・死因 0 件 | ☐ |
| `console.log` / Sentry への個人情報出力 0 件 | ☐ |
| Webhook URL がコードに直書きされていない | ☐ |
| Review / aggregateRating / ratingValue 追加 0 件 | ☐ |
| `.env*` への接触 0 件 | ☐ |

---

## 停止条件

以下に該当したら **即停止、人間に報告**。AI 判断で続行しない:

- 個人特定可能な情報を発見
- 遺影・名札・会葬礼状が判読可能な画像
- フォームから個人情報が外部にログ出力されている
- Review / aggregateRating / ratingValue の追加要望（根拠と顧客同意が必要）
- 確信が持てない判断（リスクが残る場合は停止が正解）
