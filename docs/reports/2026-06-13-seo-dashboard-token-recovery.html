SEO ダッシュボード復旧：refresh_token 失効の診断と恒久対策

作成日：2026-06-13対象：/admin/seo/担当：Claude Code

社内記録（Web非公開・noindex）。秘密情報（トークン値・鍵）は一切記載していません。

事象：/admin/seo/?range=7d で「データを取得できませんでした」。前回も同様に発生（約 1 週間ごとの再発）。

1. 診断（秘密情報を出さずに検証）

OAuth とサービスアカウントの両認証を、値を一切出力しない診断スクリプトで検証（実行後に削除）。

認証方式結果解釈
OAuth refresh_token（現行コードが使用）invalid_grantリフレッシュトークン失効。これが取得失敗の直接原因
サービスアカウント（env に存在・未使用）ERR_OSSL_UNSUPPORTEDenv の秘密鍵が Node で解析不可。代替に使えない（過去経緯：SA は GSC 側でユーザー追加不可だった）

lib/search-console/client.ts は OAuth トークンのみ使用。失効で loadDashboardData が throw → data.ok=false → 当該表示。

2. 根本原因（再発する理由）

Google OAuth 同意画面が「テスト中」公開ステータスのままだと、発行される refresh_token は 7 日で自動失効する（Google 仕様）。約 1 週間ごとに落ちるのはこのため。既存 Runbook §10 の「refresh_token は無期限」という記述は、テスト中ステータスでは誤り。

3. 恒久対策（ユーザー選択：本番公開で恒久化）

  • OAuth 同意画面を「本番（In production）」に公開すると refresh_token は実質無期限になる。
  • webmasters.readonly は機密スコープだが、本番公開に Google の審査は必須でない（未審査でも公開可。同意時に「確認されていません」警告が出るのみ、社内 1 ユーザーなら通過で問題なし）。
  • 本番公開後に refresh_token を取り直す（テスト中発行の旧トークンは 7 日失効対象のまま）。

4. 今回の変更（ドキュメント）

  • docs/operations/seo-dashboard/README.md を修正：
    • §5.1 公開ステータスの記述を「テスト中＝7 日失効／本番公開で恒久化（未審査でも可）」に全面改訂
    • §10 の「refresh_token は無期限」を公開ステータス依存の正しい記述に訂正
    • §11 トラブルシュートの invalid_grant 行に「週次再発＝テスト中。本番公開で恒久解決」を追記
  • コード変更なし（認証方式は OAuth 継続。client.ts 等は無変更）。

5. 復旧手順（ユーザー操作・要対応）

  1. 本番公開：console.cloud.google.com/apis/credentials/consent →「アプリを公開 / PUBLISH APP」→ 確認。
  2. トークン再取得：node --env-file=.env.local scripts/get-refresh-token.mjs を実行 → tmp/auth-url.txt の URL をブラウザで開き、GSC 閲覧権限のある Google アカウントで承認（「確認されていません」警告は[詳細]→[移動]で通過）→ tmp/refresh-token.txt に新トークンが出力。
  3. env 更新：新トークンを .env.local と Vercel（Production/Preview/Development）の GOOGLE_OAUTH_REFRESH_TOKEN に設定。
  4. 反映：Vercel 再デプロイ → /admin/seo/ で表示確認。tmp/auth-url.txt・tmp/refresh-token.txt を削除。

確認結果：ドキュメント修正のみ。秘密情報は診断・レポートとも一切出力・保存していない（診断スクリプトは実行後削除）。コード・公開サイトへの影響なし。

6. 残課題

  • 要対応 ユーザーによる本番公開＋トークン再取得＋env 更新（上記 §5）。完了後にダッシュボード復旧。
  • 将来 サービスアカウント方式は現状の鍵が解析不可・GSC 追加不可の経緯あり。恒久運用は OAuth 本番公開で十分。
