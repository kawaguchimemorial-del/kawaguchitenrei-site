1. できるようになったこと

GTM と GA4 を API から操作できるようにした。scripts/get-refresh-token.mjs に gtm / ga4admin / measure のスコープを追加し、Cloud プロジェクト 487251905710 で Tag Manager API と Google Analytics Admin API を有効化した。

途中の誤り：最初に「APIは両方とも有効」と報告したが誤りだった。スコープが足りない状態では権限エラーが先に返るため、有効化の状態まで見えていなかった。スコープを通して初めて「未有効」と分かった。

3. lp_* の「届いていない」は誤診断だった

9/11の結論「GA4へ届けるにはGTMに転送タグが1つ必要」は誤りだった。実際に作って公開したところ、すべての lp_* が2件ずつ記録される二重計上になった。1回のタップで lp_click_tel が2件、既存の click_tel は1件。

切り分けの手順

確認結果
ブラウザの dataLayer を直接確認lp_view 1件・lp_click_tel 1件。アプリは正常
代理店コンテナにGA4タグがあるか配信中の gtm.js を取得して確認 → なし
タグの発火トリガー6タグすべて1つずつ、ブロック条件なし
追加したタグを一時停止して実測lp_view 1件・lp_click_tel 1件。タグ無しで正しく届いていた

本番JSを取得したところ transport_type と send_to が含まれていた。lib/lp-analytics.ts の書き換えはコミットもデプロイもされておらず、本番は一貫して gtag コマンド形式で動いていた。gtag のコマンドは GTM の data layer 上でイベント形式に変換されるため、追加したトリガーもそれに反応してもう一度送っていた。これが二重計上の正体。

9/11の分析が根拠にした「generate_lead は届くのに lp_generate_lead は0」という比較は、すべて2026-08-28の1日分だった。その時点では実際に不具合があったが、9/06の差し戻し以降は正常に動いていた。90日の合計が古い不具合に引きずられていただけで、直近を確認していれば別の結論になっていた。

もう一つの見落としは母数である。/lp/ は8/26以降の合計で表示70件しかない。広告はいまも旧LPに着地しているため人が来ていない。この母数で「0件だから壊れている」と判断すべきではなかった。

4. プラン詳細の導線をLP内で完結させた

プランカードは /plan/（本サイト）へリンクしていたため、開いた人は広告の着地先から出ていた。そこからは lp_* も代理店のコンバージョンタグも発火しない（どちらも /lp/ 限定）。旧LPでも8月の外部リンク31件中24件が本サイト宛てで、同じ漏れが起きていた。

5. 反省

  • docs に書かれた前提を、確認せずに引き継いだ。「旧LPのGA4は見られない」は1か月以上そのまま扱われ、代理店にも権限申請を依頼していた。
  • 集計期間の合計だけを見て原因を断定した。日別で見れば9/06以降は正常だった。
  • 母数を見なかった。表示70件のページで「0件」を異常と判断した。
  • 確かめる前に本番へ公開した。転送タグは仮説の段階で公開してしまい、二重計上を起こした。切り分けのために利用者に何度もタップを依頼することになった。
