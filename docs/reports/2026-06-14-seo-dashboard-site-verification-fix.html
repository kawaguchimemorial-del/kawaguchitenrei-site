SEO ダッシュボード復旧：403 権限不足の診断と所有権確認による解消

作成日：2026-06-14対象：/admin/seo/担当：Claude Code

社内記録（Web非公開・noindex）。秘密情報（トークン値・鍵・メールアドレス）は一切記載していません。

事象：前日（6/13）にトークン再取得まで進めたが、/admin/seo/?range=7d が再び「データを取得できませんでした」。前回の invalid_grant（失効）とは別原因。

1. 診断（秘密情報を出さない一時スクリプト・実行後削除）

値を一切出力しない診断スクリプトを tmp/ に作成し、refresh_token の生死とアカウント権限を検証した（実行後に削除）。

検証項目結果解釈
refresh_token でアクセストークン取得成功トークンは有効。前日の再取得は成立していた（＝失効ではない）
searchanalytics.query403 forbidden「User does not have sufficient permission for site」
sites.list（アカウントが見えるプロパティ）https://kawaguchitenrei.com/ ＝ siteUnverifiedUser権限レベルが「未確認ユーザー」。GSC API はこの権限ではデータ照会不可

2. 根本原因

前日トークンを再取得した際、OAuth 同意画面で承認したアカウントが、対象プロパティ（URLプレフィックス型 https://kawaguchitenrei.com/）の 正規ユーザーではなく「未確認ユーザー（siteUnverifiedUser）」だった。Search Console API でデータ照会するには Owner / Full / Restricted のいずれかが必要で、未確認ユーザーは 403 になる。トークンの問題ではなく アカウントのプロパティ権限の問題。

3. 対応（所有権確認＝B案より直接的な解決）

当該アカウントで Search Console の所有権確認（HTMLファイル方式）を行い、Owner に昇格させる方針を採用。Owner になれば、現在 env にある（有効な）refresh_token がそのまま権限を持つため、トークン再取得や env / Vercel の更新は不要。

  • Google 発行の確認用 HTML（google49b5da2b44a51992.html）は、当初 public/images/tmp/serch/ に置かれていたため、配信 URL がルートにならず確認できない状態だった。
  • Next.js は public/ をサイトルートに配信するため、ファイルを public/ 直下へ移動し、https://kawaguchitenrei.com/google49b5da2b44a51992.html で配信されるようにした。
  • 確認状態維持のため、このファイルは削除せずコミットして本番に残す（Google の指示どおり）。

4. 変更内容

ファイル変更

public/images/tmp/serch/空になったため削除

コード・公開ページ本体への変更なし。認証方式は OAuth 継続（lib/search-console/* 無変更）。

5. 確認結果

  • npm run build 成功（エラーなし・従来どおりのルート構成）。
  • 本番配信を実測確認：https://kawaguchitenrei.com/google49b5da2b44a51992.html がデプロイ後 HTTP 200 ＋ google-site-verification を返すことを確認。
  • ユーザーが Search Console で所有権確認を実行 → ダッシュボード復旧（データ表示）を確認。

後片付け：前日のトークン再取得で生成され平文で残っていた tmp/refresh-token.txt（refresh_token の平文）と tmp/auth-url.txt を、ユーザー承認のうえ削除。秘密情報は診断・レポートとも一切出力・保存していない（診断スクリプトは実行後削除）。

6. 今後のアクション・メモ

  • 完了 ダッシュボード復旧。
  • 維持 public/google49b5da2b44a51992.html は所有権確認の維持のため削除しない。
  • 参考 今回は「失効」ではなく「権限不足」。今後ダッシュボードが落ちたら、まず①トークン失効（invalid_grant）か②権限不足（403 / siteUnverifiedUser）かを切り分ける。トークン再取得時は必ず GSC で Owner/Full 権限を持つアカウントで承認すること。
  • 将来 refresh_token の 7 日失効を避ける恒久対策（OAuth 同意画面の本番公開）は前日レポート参照。
