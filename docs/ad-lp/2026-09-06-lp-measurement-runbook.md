# 広告LPと本サイトを分ける計測運用手順

作成日: 2026-09-06 / 担当: Codex / 適用開始: 新LP公開後。広告の移行日は会議で決定する。

## 集計の原則

同一GA4プロパティを使い、セッション入口で「LP入口」「本サイト入口」「内部入口」「入口不明」に分ける。同一人物の別セッションは別訪問。同じセッションのLP→本サイト遷移はLP入口のまま。ページの閲覧場所を測る指標と、最初の集客元を測る指標を混同しない。

本サイトの成果は、本サイト入口に限定したうえでOrganic Searchを抽出する。Paid Search、Cross-network、Display等の広告チャネルは別表示。LP入口全体にもDirect等があるため「LP入口＝広告クリック」としない。広告クリック数とGA4セッション数が常に一致するとも考えない。

LP内で起きたイベントを全部LP入口の成果として数えるわけではない。本サイト入口からLPへ移動した同一セッションのlp_*イベントは、本サイト入口レポート側に残る。入口不明の値を本サイトへ含めない。GSCは自然検索のクリック・表示を見る別のデータ源であり、広告クリックを含まない。

## 毎回実行するコマンド

リポジトリのルートで `node --env-file=.env.local scripts/ad-lp-report.mjs --start 2026-09-01 --end 2026-09-03` を実行する。期間は必ず対象の開始日・終了日へ変更する。将来の日や本日の未確定値を週次比較へ混ぜず、期間・プロパティのタイムゾーン・処理遅延を確認する。

既存のGA4_PROPERTY_IDと、既存のGoogle認証を利用する。認証値を開く・画面表示する・報告書へ貼る必要はない。認証の再発行や権限変更はこの手順に含まない。失敗時は区分・HTTPステータスだけを出力し、生のエラーや資格情報をログへ出さない。

取得する内容は各区分のチャネル別sessions/engagedSessionsとイベント別eventCount。結果はtmp/ad-lp-report-開始日-終了日-時刻.json。tmpはGit管理外。スクリプトはGA4設定を変更しない。5区分目のmain_organicはmain_entryの内数なので、全体合計へ足してはいけない。activeUsersを区分間で足して総人数とする方法も使わない。

2026-09-06の実行で10レポート取得成功。2026-09-01〜03のセッションはLP2、本サイト95、内部1、入口不明7。本サイトOrganic Search73は95の内数。この値は新LP公開前の動作確認用であり改修効果ではない。

## GA4画面で同じ見方を作る

管理画面に保存済みの新しい探索を作成したわけではない。編集権限がある担当者は、以下を設定するとチームで同じ条件を再利用できる。APIスクリプトの集計は探索の作成やカスタムディメンションの登録がなくても動作する。

- 「ランディングページ」レポートまたは探索で、期間と本番ホストを指定する。対象ホストは kawaguchitenrei.com と www.kawaguchitenrei.com。
- LP用はランディングページ＋クエリ文字列が正規表現 `^/lp(/.*|\?.*|$)` に完全一致するものを含める。
- 本サイト用は上記LPに加え、内部入口の正規表現 `^/(admin|post|voice/survey)(/.*|\?.*|$)` と `(not set)` を除外する。
- 探索ではユーザーセグメントではなくセッションセグメントを作る。入口条件で対象セッションを選び、そのセッションの行動を確認する。
- 流入分析には「セッションのデフォルトチャネルグループ」、必要なら「セッションの参照元/メディア」「セッションのキャンペーン」を使用する。初回ユーザーの参照元へ置き換えない。
- SEOの資料には「本サイト入口＋Organic Search」と明記する。旧SEOダッシュボードや既存search-console-audit.mjsのGA4全体値を、除外済みだと思って引用しない。

入口はセッションの最初のページビューのパスとクエリで決まる。[Google公式のランディングページ説明](https://support.google.com/analytics/answer/12931766?hl=en)。標準レポートの初期表示や機能名はプロパティの構成により異なる。

## LPイベントの辞書

| イベント | 発生条件 | 指標の意味 |
|---|---|---|
| lp_view | LP配下の画面が表示されたとき | ページ表示の補助。セッション数・広告クリック数ではない |
| lp_click_tel | LP内の計測対象電話リンクを押す | 電話タップ。実通話ではない |
| lp_contact_open | LP内の事前相談リンクを押す | フォームへの移動意図。送信ではない |
| lp_plan_open | LPのプラン詳細リンクを押す | 料金・内容への関心 |
| lp_form_start | 専用フォーム内に最初にフォーカスが入る | 入力開始の代理指標。画面を再訪すれば再計測され得る |
| lp_generate_lead | 専用フォームの成功表示 | 送信成功表示。保存された有効相談の確定件数ではない |
| lp_directions | 地図リンクを押す | 場所への関心。来館ではない |

固定パラメータはsite_area=ad_lp、lp_variant=2026-09-consultation-v2。cta_placementでhero/header/sticky/bottom/contact_form等の位置を識別し、plan_slugはプラン詳細クリック時だけ送る。イベントのpage_locationはorigin＋pathnameとし、クエリは送らない。フォームの名前、連絡先、相談本文、病状、入力値は送らない。既存の通常page_viewのURL収集仕様を変更したわけではないので、そもそも個人情報をURLへ入れない。

位置別・版別の集計が必要な場合だけ、GA4「管理→カスタム定義」でcta_placement、lp_variant、site_area、plan_slugをイベントスコープのカスタムディメンションとして登録する。今回Google側では登録していない。登録前の過去値への遡及を前提にしない。[Google公式のカスタムディメンション手順](https://support.google.com/analytics/answer/14239696?hl=en)。

## 二重計上とGoogle Adsの切替前チェック

既存generate_lead(form_type=lp_contact)は互換のため維持。lp_generate_leadは同じ成功表示に対する追加の識別用イベントである。両方を足した「問い合わせ数」は誤り。既存click_telとlp_click_telも合算しない。LPを経由して本サイトの別フォームで相談した場合は、LP入口セッションのgenerate_leadとして別途確認できる。

LPイベントは既存Googleタグへsend_toを指定して送っており、GTMで同名の送信タグを新設する必要はない。GTMのdataLayerイベントオブジェクトだけを探すテストでは確認できないため、Googleタグの送信とGA4受信を確認する。既存タグの設定変更により互換性が変わる可能性は残る。[Google公式のルーティング仕様](https://developers.google.com/tag-platform/gtagjs/routing)。

- 会議前に、現在のGoogle Adsの主要/補助CV、GA4インポート、電話クリックタグ、通話計測を一覧化する。今回それらを設定変更したわけではない。
- フォーム送信をGoogle Adsへ渡す場合、同じ行動を既存generate_leadとlp_generate_leadの両方から主要CVへインポートしない。既存対応表を見て片方を選ぶ。
- lp_view、lp_contact_open、lp_form_start、lp_plan_open、lp_directionsを「問い合わせ完了」として扱わない。
- 電話タップは実着信と分ける。主要CVを何にするかは実際の通話計測との対応を確認して決める。全タップを有効相談だとする入札評価は避ける。
- 新イベントのGA4リアルタイム受信、通常レポートへの反映、保存・通知との対応を切替前に確認する。テスト用の問い合わせを送る場合は通知先と削除・除外方法を先に決める。

広告の自動タグ設定、最終ページURL、遷移後の計測を代理店と確認する。サイト内リンクへ広告用UTMを付けて流入元を上書きしない。同一ドメイン内でLPと本サイトを移動するだけなら、別サイト同士のクロスドメイン設定を追加する理由はない。旧ドメインと行き来する導線が残る場合は別途設計する。

## テスト・内部利用の除外

日常の確認は本番 /lp/?analytics=off を開く。フラグは同じブラウザに保存される。localhost、Vercelプレビュー、内部パスは既存ポリシーでも除外。実受信を試す担当者はこの除外が有効だとイベントが送られないことを理解したうえで、限定的に?analytics=onを使い、終了後は?analytics=offへ戻す。除外フラグを外したまま日常確認しない。

APIスクリプトは取得だけで、GA4へテストイベントを送らない。電話アプリの起動やフォームの実送信を、単なる表示検証として繰り返さない。

## 週次報告の書式と移行判定

毎週、対象期間・変更日・対象キャンペーン・入口条件・チャネル・広告費/クリック・セッション・電話タップ・フォーム成功表示・実着信・有効相談・施行の順で記録する。取得できない項目は未取得と書き、タップで代用しない。広告費÷タップ単価と広告費÷有効相談単価は別の指標である。

Google Adsの広告帰属とGA4のセッション入口は異なる見方なので、両者を合算しない。旧LPと比較するときは期間、配信面、検索語句、料金表現、CV定義、計測可能性の違いを明記する。同時に広告設定も変わったら、LP改修だけの効果とはしない。

次回会議日・移行日は未確定。決定後に日付と担当を追記し、初週は不具合・欠損の点検を優先する。低い件数の短期間比較で勝敗を決めず、比較可能な条件と十分な観測期間を会議で合意する。

## 後任への注意

正本はこの運用手順と同日の再設計記録。古い広告LP資料の「別ドメインだから混ざらない」は、新LPへ移行した後には当てはまらない。新LPのnoindexとsitemap除外は検索結果への出し分けであり、GA4の計測分離設定ではない。

認証値は.env.localを開かず既存の--env-fileで利用する。新たなプロパティ、Google Adsコンバージョン、GTMタグ、カスタムディメンション、共有権限の追加は、それぞれ実施記録がなければ未設定と扱う。分離集計スクリプトの成功だけを「広告移行完了」と報告しない。
