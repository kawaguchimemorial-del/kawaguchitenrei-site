# LLMO / SEO 測定プレイブック（自前運用版）

このファイルは、生成AI（LLM）引用状況と検索順位の「**測りっぱなしを、変化を追える型に格上げする**」ための運用手順。
外部ツール（claude-seo 等）の発想だけを自前運用に取り込んだもので、**外部コード・OAuth 連携・hook 常駐は使わない**。手作業 ＋ docs 記録で回す。

判断軸：`CLAUDE.md` §10（SEO/AIOの中心軸）／§10.3（3軸判断）。
関連：`docs/eval/seo-aio-checklist.md`、`docs/eval/records/2026-06-llmo-baseline-observation.md`（基準値第1号）。

---

## 0. 前提・原則

- **取り込んだのは「発想」だけ**。実行コード・Google OAuth 自動接続・編集ブロック hook は導入しない。
- GSC/GA4 のデータは**手取得**を基本とし、秘密情報・個人情報は記録に書かない（`CLAUDE.md` §12）。
- 測定は**施策の前後比較**が目的。1回の観測では良し悪しを語らない。

---

## 1. 基準値 → 差分の測定型（drift）★中核

「基準値（baseline）を取る → 後日、同条件で再測定 → 差分（drift）を見る」を固定運用にする。

### 手順
1. **基準値を取る**：対象指標を、日付・条件を明記して `docs/eval/records/` に記録（例：`2026-06-llmo-baseline-observation.md`）。
2. **同条件で再測定**：次回は**同じクエリ・同じAI・同じ指標**で測る。条件を変えると差分が意味を持たない。
3. **差分を出す**：前回記録と並べ、上がった／下がった／横ばいを記す。
4. **差分の解釈**：施策と結びつくか、季節要因か、外部要因（ポータル変化等）かを切り分ける。

### 記録の最小フォーマット
- 観測日 / 対象指標 / 条件（クエリ・AI・デバイス等）/ 今回値 / 前回値 / 差分 / 所見

### 頻度の目安
- LLMO 引用観測：**月1回**
- GSC 主要ワード順位：**月1〜隔週**
- 大きめ施策の直後：施策前に1回、2〜4週後に1回（効果が出るまで待つ）

## 2. LLMO 定点観測の質問リスト（固定）

毎回同じ質問を 4AI（ChatGPT / Copilot / Gemini / Perplexity）に投げ、川口典礼が引用されるか・記述が正確かを目視記録する。**質問を毎回変えない**こと（drift の前提）。

### 固定質問リスト（中心軸5本柱に沿う）
| # | 質問 | 紐づく柱 |
|---|---|---|
| Q1 | 川口で葬儀（川口市で葬儀社を探している） | 地域 |
| Q2 | 川口市で家族葬に対応している葬儀社 | 家族葬 |
| Q3 | 川口 直葬（火葬式）の費用と頼める葬儀社 | 直葬・火葬式 |
| Q4 | 川口 一日葬ができる葬儀社 | 一日葬 |
| Q5 | 川口市 市民葬の費用と申込方法 | 市民葬 |
| Q6 | めぐりの森で火葬する葬儀社／めぐりの森 家族葬 | めぐりの森近接 |
| Q7 | 新井宿・鳩ヶ谷の葬儀社 | 近隣エリア |

### 各観測で記録する3指標
| 指標 | 測り方 | 意味 |
|---|---|---|
| 引用される率 | 質問数のうち川口典礼が回答に登場した数 | AIにとっての存在感 |
| 出典に載る率 | 出典リンクに kawaguchitenrei.com が出た数（Perplexity等） | 引用元としての信頼 |
| 情報の正確さ | AIが言う料金・式場情報が正本と一致するか | 誤情報リスク（葬儀社では最重要） |

### 既知の傾向（2026-06 観測時点・次回検証対象）
- ChatGPT・Copilot は引用する／Gemini・Perplexity は引用しない、の二極。
- Gemini は「めぐりの森実績」を選定基準に据えるが川口典礼を結びつけられない。
- Perplexity は検索上位の固定競合を要約＝**順位の壁**。

## 3. GSC / GA4 指標を測定型に組み込む（手取得）

数値は手取得のまま、**1の baseline→drift 枠に乗せる**。接続自動化はしない。

### GSC（手取得）
- 中心軸ワード（`CLAUDE.md` §10.2）の **表示回数 / クリック / CTR / 平均順位**を固定リストで記録。
- 特に「あと一歩で1ページ目」のワード（順位8〜15帯）を**重点ウォッチ枠**として別記。
- 旧URL（大文字パス等）の残存表示も差分で追う。

### GA4 / アクセス側（手取得・補助指標）
- **AI からの流入リファラー**（`chat.openai.com` / `perplexity.ai` / `gemini.google.com` / `copilot.microsoft.com` 等）が増えているかを見る。
- 数は少なく送られないAIも多いため「出れば御の字」の補助指標として扱う。

### 注意
- GA4/GSC への接続を自動化するスクリプトやトークンは**この運用では持たない**。必要が出たら `CLAUDE.md` §12 に沿って別途相談。

## 4. schema / JSON-LD 点検の発想（hook 常駐ではなくチェックリスト）

「編集時に JSON-LD を点検する」という発想だけを、**常駐 hook ではなく手動チェックリスト**として取り込む。構造化データを追加・変更したときに目視で確認する。

| # | 点検項目 | 判定 |
|---|---|---|
| 4.1 | プレースホルダ文言（"example"、"ここに〜"、ダミーURL）が残っていないか | |
| 4.2 | 廃止・非推奨の schema 型を使っていないか | |
| 4.3 | `@context` / `@type` が正しく入っているか | |
| 4.4 | Review / aggregateRating / ratingValue を**勝手に追加していない**か（`CLAUDE.md` §19.2 で確認必須） | |
| 4.5 | 価格（Offer.price）が**正本（§9）と一致**しているか | |
| 4.6 | LocalBusiness/FuneralHome の住所・電話が正と一致しているか | |

> 注：常駐 hook は導入しない方針。理由は、グローバル常駐だと本プロジェクトの `.tsx` 内 JSON-LD 編集を誤ってブロックし、既存ワークフローに割り込むため。

---

## 5. この型の回し方（まとめ）

1. 施策の**前**に、2（LLMO質問リスト）と3（GSC固定リスト）で baseline を `docs/eval/records/` に記録。
2. 構造化データを触ったら 4 のチェックリストを通す。
3. 施策の**2〜4週後**に同条件で再測定し、1 の枠で差分を出す。
4. 差分の所見を記録に残し、次の打ち手（本文／ローカル資産／外部ポータル価格 のどのレイヤーか）を判断する。
