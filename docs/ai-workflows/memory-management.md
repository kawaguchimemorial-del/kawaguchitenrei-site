# メモリ管理ルール（チャット情報の保存先振り分け）

このファイルは、チャット中に得た情報をどの保存先に置くべきかを決めるルール。
情報が散らばると将来の Claude Code / 人間が判断できなくなるため、保存先と削除条件を明確化する。

最終更新: 2026-05-25

追記（2026-09-05）: ユーザーのCodex引き継ぎ依頼により、`AGENTS.md` は技術前提に加え、
既存 `CLAUDE.md` / docsへの入口、主要な作業制約、SEO/MEO/AIO・Vercelの参照先を保持する。
以下の旧分類表の「技術前提」はこの追記で拡張する。料金などの正本を複製せず、
計測値・日付付きの現状分析は `docs/seo-research/2026-09-05-site-baseline-and-codex-handoff.md` に置く。

## 1. 保存先の分類

| 保存先 | 性格 | 寿命 | 主な対象 |
|---|---|---|---|
| **CLAUDE.md** | 入口・憲法。プロジェクト全体の最重要ルール。 | 長期 | 触ってはいけないファイル / 自動 push 範囲 / 葬儀社サイトとしてのトーン |
| **AGENTS.md** | 技術前提（Next.js 訓練データ差分など） | 長期 | フレームワーク特有の注意 |
| **`skills/<slug>/SKILL.md`** | 反復実行する手順・チェックリスト | 中〜長期 | 「SEO 改善するときに必ず通る手順」 |
| **`agents/<slug>.md`** | エージェントの役割定義・停止条件 | 中〜長期 | 「研究エージェントの役割範囲」 |
| **`docs/00-05` のポリシー docs** | プロジェクト方針（人間も読む） | 長期 | プライバシー方針 / コンテンツガイドライン |
| **`docs/eval/records/<日付>-<件名>.md`** | 完了記録（過去どんな実装をしたか） | 長期（履歴として保持） | 「2026-05-25 の /saijo/ 強化記録」 |
| **`docs/operations/<カテゴリ>/<日付>-<件名>.md`** | 運用ログ（Search Console 作業ログなど） | 中期（古いものはアーカイブ可） | URL 検査ログ / 本番反映確認 |
| **`docs/seo-research/<日付>-<件名>.md`** | 調査・分析の保存版 | 中期 | 競合分析 / キーワード分析 |
| **`docs/prompts/claude-code-prompts.md`** | 再利用したい依頼文の雛形 | 長期 | 「エリアページ追加プロンプト」 |
| **Claude Code の auto-memory**（`C:\Users\...\memory\`） | 個別ユーザー設定・好み・許可済み範囲 | 長期 | 「自動 push 許可範囲」「ユーザーメール」「現在日付」 |
| **チャット内のみ**（保存しない） | 一時的な指示・確認の往復・実装中の検討メモ | 短期 | 「次にこれを試そう」「この案で進める」 |

## 2. 情報の種類別 振り分けフロー

```
情報が手に入ったら、まず以下を順番に判定する:

(1) 個人情報・秘密情報か？
    YES → 絶対に保存しない（CLAUDE.md §12・docs/04-privacy-review.md 参照）
    NO  → (2) へ

(2) プロジェクト全体の不変ルールか？（触らないファイル / トーン / 価格正本）
    YES → CLAUDE.md（既存項目に統合 or §追加）
    NO  → (3) へ

(3) 反復実行する手順か？（毎回同じステップを踏む）
    YES → skills/<slug>/SKILL.md
    NO  → (4) へ

(4) エージェントの役割定義か？（どんな入力でどんな出力を返すか）
    YES → agents/<slug>.md
    NO  → (5) へ

(5) 過去にやった作業の記録か？
    YES → docs/eval/records/<日付>-<件名>.md
    NO  → (6) へ

(6) 運用ログ（Search Console など）か？
    YES → docs/operations/<カテゴリ>/<日付>-<件名>.md
    NO  → (7) へ

(7) 調査・分析の保存版か？
    YES → docs/seo-research/<日付>-<件名>.md
    NO  → (8) へ

(8) 再利用したい依頼文の雛形か？
    YES → docs/prompts/claude-code-prompts.md に追記
    NO  → (9) へ

(9) ユーザー個別の好み・許可済み範囲か？
    YES → Claude Code の auto-memory（feedback / user / project / reference の適切な type で保存）
    NO  → (10) へ

(10) どこにも該当しない
    → チャット内のみ。次回も同じ話題が出るならどこかに保存する判断をする
```

## 3. 個別の判断指針

### 3.1 CLAUDE.md に書くべきもの

- プロジェクト全体に効く不変のルール
- 触ってはいけないファイル
- 価格正本（プラン名・税込価格）
- 葬儀社サイトとしてのトーン
- 自動 push / push 前確認 / 停止条件の概略
- 詳細は Skill / Agent / docs を参照する**索引**として機能させる

**CLAUDE.md に書かないもの**:
- 個別ページの実装詳細
- 一時的な作業状況
- 個人情報

### 3.2 Skill に書くべきもの

- 「毎回必ず通る手順」（例: SEO 改善の 7 ステップ）
- 手順内の各ステップで通すチェックリスト
- 例外的な判断が必要なケースの判定方法
- 関連する他の Skill・Agent への参照

**Skill に書かないもの**:
- 特定の実装のスナップショット（→ docs/eval/records/）
- 一時的な対処

### 3.3 Agent に書くべきもの

- エージェントの役割（何をするか）
- 入力（どんな指示を受け取るか）
- 出力（どんな成果物を返すか）
- 使う Skill
- 停止条件 / 人間承認条件
- 失敗時のフォールバック

**Agent に書かないもの**:
- 具体的な手順（→ Skill に書く）
- 特定実装の詳細

### 3.4 docs/eval/records/ に書くべきもの

- 「何月何日に、どのファイルを、なぜ、どう変更したか」の完了記録
- commit hash
- 本番確認結果
- 安全確認チェックリスト結果
- 次の候補

**docs/eval/records/ に書かないもの**:
- 再利用可能な手順（→ Skill）
- ルール（→ CLAUDE.md / skills）

### 3.5 docs/operations/ に書くべきもの

- 運用作業のログ（Search Console / Vercel ダッシュボード / 本番反映確認）
- 実施日・対象 URL・結果・次回確認目安

### 3.6 Claude Code の auto-memory に書くべきもの

- ユーザー個別の好み・許可済み範囲・苦手な進め方
- ユーザーが「覚えておいて」と明示したもの
- 過去のセッションで承認された設定

**auto-memory に書かないもの**:
- repo の事実（→ ファイルを読めば分かる）
- 個人情報・秘密情報
- 一時的な作業状況

## 4. 古くなった情報・推測・未確認情報の扱い

### 4.1 古くなった情報

- **完了記録（docs/eval/records/）は削除しない**：過去経緯として保持
- **方針 docs（docs/00-05）が古くなったら**：新版で上書きするのではなく、古い記述を残したまま追記日付付きで更新（差分が分かるように）
- **Skill が古くなったら**：手順を更新し、最終更新日を更新。大幅変更時は変更履歴を末尾に追記
- **auto-memory が古くなったら**：memory-curator agent が定期的に整理（削除 or 更新）

### 4.2 推測情報の扱い

- **推測は明示する**：「推測です」「未確認です」「Excel 由来の未確認情報です」と必ず明記
- **推測のまま docs に残さない**：確認が取れない場合は、docs にも「要確認」マークを付ける
- **価格・式場利用可否・宗派条件・空き状況・檀家条件は推測しない**：これらは推測してはいけない領域（CLAUDE.md §12・§14）

### 4.3 未確認情報の扱い

- **未確認情報を本文に断定形で書かない**：「確認のうえご案内します」「目安」と表記
- **「要確認」リストを docs に残す**：寺院公式確認待ち・本人確認待ちなど、明示的に未確認である事実を記録
- **後で確認が取れたら、要確認マークを外し、出典を併記**：「2026-05-25 寺院公式サイト確認済み」など

## 5. メモリ整理のタイミング

| タイミング | 実施内容 | 実施者 |
|---|---|---|
| **毎回の作業終了時** | 新しく得た情報を §2 のフローで振り分け、適切な保存先に書く | 実装担当 Claude Code |
| **1 週間に 1 回程度** | auto-memory の古い・重複した・矛盾するエントリを整理 | memory-curator agent（手動起動） |
| **大きな方針変更時** | CLAUDE.md・docs/00-05 を更新、関連 Skill / Agent を見直す | 人間 + AI 共同 |
| **新しい Skill / Agent を追加したとき** | `docs/ai-workflows/skill-index.md` の §4 表に必ず追記 | 実装担当 Claude Code |

## 6. 「これは保存すべきか？」迷ったら

以下を順番に問う:

1. **次の Claude Code セッションで同じ判断をするときに、この情報がなければ困るか？** → YES なら保存
2. **コードを読めば分かることか？** → YES なら保存しない（コードを読めばよい）
3. **個人情報を含むか？** → YES なら絶対に保存しない
4. **どこに保存すれば次回見つかるか？** → §2 のフローで決定

迷ったら、**保存しない方を選ぶ**。情報が散らばる害の方が、忘れる害より大きい。
ただし「ユーザーが明示的に覚えておいてと言った場合」は迷わず保存する。
