# AI 作業の品質評価指標 (eval-metrics)

川口典礼サイトでの AI 作業について、品質を継続的に測るための指標を定義する。
施策の振り返り（`docs/eval/records/`）で参照できるよう、指標は **数えられる形** で書く。

「評価できないものは改善できない」。AI に任せた領域こそ、定量的な評価軸が必要。

---

## 1. 評価対象

- SEO / AIO 改善
- エリアページ追加
- 構造化データ（JSON-LD）
- Search Console 運用
- 画像管理
- Privacy Review
- Claude Code 作業全般
- docs 記録

---

## 2. ビルド・本番反映系の指標

| 指標 | 定義 | 目標 | 計測方法 |
|---|---|---|---|
| **build 成功率** | 全コミットのうち、push 後の Vercel build が初回で成功した割合 | 100% | Vercel Dashboard / `vercel deployments` |
| **本番 URL 200 確認率** | 公開対象 URL の本番反映後 HTTP 200 確認の割合 | 100% | `curl -sw "%{http_code}"` |
| **canonical 整合率** | 公開ページの canonical が trailingSlash あり・リクエスト URL と一致している割合 | 100% | HTML スクレイプ |
| **sitemap 反映率** | 公開対象 URL のうち sitemap.xml に含まれている割合 | 100% | `/sitemap.xml` 取得→比較 |
| **画像 200 配信率** | 新規追加画像のうち本番で 200 / 正しい Content-Type で配信される割合 | 100% | `curl -sw "%{http_code} %{content_type}"` |

## 3. 構造化データ系の指標

| 指標 | 定義 | 目標 | 計測方法 |
|---|---|---|---|
| **JSON-LD 検証率** | 公開ページ全 JSON-LD のうち、Rich Results Test / Schema Markup Validator でエラーが出ない割合 | 100% | 各ツールでの目視 + サンプリング |
| **JSON-LD 主要要素必須化率** | エリアページの `BreadcrumbList` / `FAQPage` / `FuneralHome` が全揃っている割合 | 100% | HTML 内 `<script type="application/ld+json">` の有無 |
| **areaServed 整合率** | `FuneralHome.areaServed.name` が実際の対応地域と一致している割合 | 100% | 目視レビュー |

## 4. コンテンツ品質・トーン系の指標

| 指標 | 定義 | 目標 | 計測方法 |
|---|---|---|---|
| **禁止表現混入件数** | 公開ページ全文での「最安」「必ず」「絶対」「追加費用なし」「総額確定」の出現件数 | 0 | `grep -c` |
| **未確認距離・所要時間表現の新規混入** | 新規ページ・新規セクションでの「車で約N分」「徒歩N分」の追加件数（既存事実確認済みは除く） | 0 | レビュー時の手動カウント |
| **断定表現混入件数** | 「必ず」「絶対」「100%」「確実に」「断言します」の出現件数 | 0 | `grep -c` |
| **競合誹謗混入件数** | 競合他社固有名詞と優劣表現の組み合わせ件数 | 0 | レビュー時の手動カウント |
| **価格表記の正本一致率** | 公開価格表記のうち `CLAUDE.md §9` の正本と一致する割合 | 100% | 目視レビュー |

## 5. Privacy / 個人情報リスク系の指標

| 指標 | 定義 | 目標 | 計測方法 |
|---|---|---|---|
| **個人情報リスク検出件数（PR レビュー時）** | フォーム / Webhook / 公開画像 / 口コミ / 施工事例の変更で、PR レビュー時にリスクが指摘された件数 | 0 | `docs/04-privacy-review.md` チェックリスト |
| **Privacy Review 実施率** | 該当領域の変更のうち Privacy Review が文書として残された割合 | 100% | `docs/eval/records/` 内の Privacy 章の有無 |
| **`.env*` 誤参照件数** | `.env*` を Read / Edit しようとした件数 | 0 | Bash / Read 履歴 |
| **シークレット混入件数** | コード・コミット・docs に Webhook URL / API キー / トークンが残った件数 | 0 | `git log -p` での grep + レビュー |

## 6. AI 作業プロセス系の指標

| 指標 | 定義 | 目標 | 計測方法 |
|---|---|---|---|
| **人間の修正量** | AI が出した成果物のうち、人間が修正した行数 / 全行数 | 段階的に低下 | git diff |
| **作業ログ保存率** | 主要施策のうち `docs/eval/records/` または `docs/operations/` に記録された割合 | 100% | docs 棚卸し |
| **完了記録 docs 作成率** | 完了とみなした施策のうち完了記録 docs を作成した割合 | 100% | 同上 |
| **Search Console 作業記録率** | Search Console 上の手動作業のうち記録 docs を作成した割合 | 100% | `docs/operations/search-console/` 棚卸し |
| **再利用プロンプト化率** | 同じ依頼が 2 回以上来た作業のうち `docs/prompts/` または Skill に切り出された割合 | 段階的に上昇 | docs 棚卸し |
| **Claude Code 手戻り件数** | AI が出した成果物を「やり直して」と差し戻した回数（1 施策あたり） | 段階的に低下 | 振り返り時の自己申告 |

## 7. SEO / AIO 系の指標

| 指標 | 定義 | 目標 | 計測方法 |
|---|---|---|---|
| **対象キーワードでの上位 10 位以内化率** | バッチ単位の主要キーワードでの 30 日後 上位 10 位以内獲得率 | 段階的に上昇 | Search Console / 手動チェック |
| **インデックス登録率** | 公開後 7 日時点で Search Console 上「インデックス登録済み」になった URL の割合 | 80% 以上 | Search Console |
| **クリック率（CTR）改善** | metaTitle / metaDescription 改修ページの CTR が前期比でプラス | プラス維持 | Search Console |
| **AI 検索引用率** | 主要 AI 検索エンジン（Bing Copilot / Google AI Overview など）で当サイトが引用される割合 | 計測手段確立を優先 | 手動チェック（サンプリング） |

## 8. 指標の使い方

### 8.1 施策ごとの記録

施策完了レポート（`docs/eval/records/YYYY-MM-<件名>.md`）に、上記指標から **関係するものを抜粋して数値を残す**。
全指標を毎回測る必要はない。施策の性質に合うものだけで OK。

### 8.2 月次レビュー

月に 1 回、`docs/eval/records/` を棚卸しして、以下を集計：

- build 成功率（push 回数 vs 失敗回数）
- 本番 URL 200 確認率
- 禁止表現混入件数
- 個人情報リスク検出件数（あれば）
- 完了記録 docs 作成率
- Search Console 作業記録率

集計結果は `docs/eval/records/YYYY-MM-monthly-review.md` として保存（必要に応じて）。

### 8.3 指標の追加・削除

実運用で「測れない / 意味がない」と判明した指標は削除する。
新しいリスクが見えたら指標を追加する。指標自体も育てる。

## 9. 計測の自動化候補

以下は将来 Hook / Skill / CI として自動計測したい：

- 禁止表現の混入チェック（`grep -c` を CI で）
- canonical 整合チェック（build 後の HTML を抽出して照合）
- sitemap 反映チェック（公開対象 URL 一覧と `/sitemap.xml` の比較）
- 個人情報らしき文字列の検出（氏名・電話・メール・住所パターン）

自動化の優先度は `ai-operations-roadmap.md` の Phase 2 以降で検討。

---

## 10. 注意

- これらの指標は **AI を萎縮させるためではなく、AI を安心して使うため** に存在する
- 数値だけを追って「数字を出すための作業」をしないこと
- 数値が悪化したときは、ルールを厳しくするのではなく、**何が起きたのか**を見にいく
- ユーザー（ご遺族）にとって本当に価値のある改善が、最終的な評価軸であることを忘れない
